Everything Worked — Until We Actually Checked

Our npm → pnpm migration uncovered a phantom dependency silently hiding in production, a Jest 30 resolver that wouldn't cooperate, and a Docker setup that was wrong from day one.

Tech Stack: Node.js · pnpm · Jest · Docker

Adarsh · 8 min read

There's a particular kind of dread that comes from discovering your software has been working by accident — not by design, but by coincidence. A hidden assumption that held up locally, sailed through CI, shipped to production, and nobody noticed because nothing explicitly broke.

That’s exactly where we found ourselves when we migrated from npm to pnpm while developing a production-grade cashout service. What we expected was a routine tooling upgrade. What we got was a mirror held up to our dependency management — and the reflection wasn’t clean.

This is the full story: why we made the switch, what broke, why each thing broke (not just that it did), and what we'd tell anyone else planning the same migration.

What Even Is pnpm?

💡 Concept — pnpm

pnpm (performant npm) is an alternative Node.js package manager. Where npm and yarn install packages into a flat, hoisted node_modules directory, pnpm uses a content-addressable store — a global cache on your machine where each version of every package is stored exactly once, with symlinks connecting projects to only what they actually declared. The result: faster installs, significantly less disk usage, and crucially — strict dependency isolation that prevents packages from accessing anything they never formally declared.

The promise is simple: faster, leaner, and more correct than npm. But "more correct" cuts both ways. pnpm will fail loudly on things npm silently permitted. For most teams, that's the entire point — you want those failures in your terminal, not waiting to surface in a container at 2am on a Friday.

Why We Made the Switch

Our reasons were practical, not ideological:

  • Build reproducibility. npm's install behavior can drift subtly across machines and environments. pnpm's lockfile-driven installs are deterministic by design — same dependencies, same structure, every single time.
  • Performance. The content-addressable store means packages shared across projects are stored once and symlinked rather than duplicated. Installs on shared CI machines become dramatically faster over time.
  • Production confidence. We were containerising the app for deployment. We wanted the dependency tree inside the Docker image to be an accurate representation of what was declared — not an artefact of npm's hoisting behavior.

Reasonable goals. But switching package managers on an active, production-bound codebase is rarely as simple as running a single command. Here's how it actually went.

How npm and pnpm Handle Dependencies Differently

Before getting into what broke, it's worth understanding the architectural difference at the root of almost every issue we hit.

Fig 1. npm hoists everything into a flat directory — even packages you never declared become reachable. pnpm isolates each package strictly. If you didn't declare it, you can't use it.

The First Crack: A Dependency We Never Declared

The very first error after switching to pnpm and running the app was this:

runtime error
Error: Cannot find module 'json-bigint'

Confusing at first glance. We could see require('json-bigint') right there in the source. The file existed. But searching package.json — it wasn't there. Not in dependencies, not in devDependencies. It had simply never been declared.

With npm, this had worked silently for the entire life of the project. The reason: some other package in our dependency tree depended on json-bigint, and npm hoisted it up to the top-level node_modules so our code could reach for it as if it were installed directly. Classic npm — helpful to a fault.

⚠️ Concept — Phantom Dependencies

A phantom dependency (also called an implicit or ghost dependency) is a package your code uses but doesn't explicitly declare in package.json. With npm's flat hoisting, these can work silently for years. The danger: if the package that actually declared it upstream updates or removes it, your build breaks — with no warning, no clear error message, and no obvious pointer to the root cause. You've been depending on someone else's transitive dependency without knowing it.

pnpm's strict isolation model doesn't allow this. Each package can only access what it has declared. Our app had been secretly depending on json-bigint through a transitive chain — and pnpm exposed that as the latent defect it was.

The fix took ten seconds:

terminal
pnpm add json-bigint

But the real value here wasn't the fix. It was the signal. Had that transitive dependency ever been removed or version-bumped away upstream, the failure would have landed in production with no direct explanation. pnpm surfaced that risk before it could matter.

The Jest 30 Surprise

Dependencies clean, time to run the test suite. We ran pnpm test, and Jest 30 — our test runner — threw this immediately:

jest output
Module <rootDir>/tests/__config__/jest.setup.js was not found

The setup file clearly existed. The path in jest.config.js was correct. Nothing had moved. Something deeper was failing and surfacing as a misleading "file not found" error.

What was actually happening

Jest 30 introduced a new file resolution engine called @unrs/resolver — a Rust-based native module that replaces the previous pure-JavaScript resolver. It's faster, but it depends on platform-specific binary bindings that need to be present and correctly accessible at runtime.

💡 Concept — @unrs/resolver and native bindings

@unrs/resolver is Jest 30's new file resolution engine, written in Rust and compiled to a native Node.js addon. Distributed as optional platform dependencies (separate packages per OS/architecture), it relies on these binaries being reachable at runtime. Under npm, optional dependencies are installed permissively and fallback behavior masks failures. Under pnpm's stricter optional dependency handling, if the binary binding isn't found in the expected location, the resolver doesn't gracefully degrade — it fails in a way that surfaces as a completely unrelated-looking "module not found" error. The misleading error message is the worst part: it sends you debugging the wrong thing entirely.

The pragmatic fix: step back to Jest 29, which uses a pure-JavaScript resolver with no native binary dependencies and no platform-specific complications.

terminal
pnpm add -D jest@29

Jest 29 ran cleanly and reliably. The tradeoff is missing some Jest 30 features and performance improvements, but for a production-bound project, "stable and reliable" wins over "newest" without question. We'll revisit Jest 30 compatibility when the pnpm ecosystem fully catches up to it.

Docker: The Container We Were Building Wrong

Tests passing, dependencies clean. Time to build the Docker image. The build failed on the first attempt:

docker build error
cannot copy to non-directory: node_modules/...

The root cause

Our Dockerfile used a common but problematic pattern: COPY . . to copy the entire project directory into the container — including node_modules. Our local node_modules had been installed by npm and had a flat structure. But pnpm uses a symlink-based structure in .pnpm/. When Docker tried to copy an npm-style node_modules into a container where pnpm was attempting to install its own version, the two structures conflicted in a way Docker couldn't resolve.

💡 Concept — Why you should never copy node_modules into Docker

Every package manager structures node_modules differently — npm uses flat hoisting, yarn uses hoisting with workspaces, pnpm uses a symlinked virtual store. When you COPY a locally-installed node_modules into a container and then attempt to install again, you get a collision between two different structural models. Worse: local installs often include native binary modules compiled for your machine's architecture, which won't run in the container's Linux environment. The rule is simple: always install dependencies inside the container from a lockfile. Never copy them in from the host.

Fix 1 — .dockerignore

The first step was ensuring Docker never touched our local node_modules in the first place. Without a .dockerignore, Docker's build context includes everything — and that means your local artifacts follow you into the container whether you intended it or not.

.dockerignore
node_modules
.pnpm-store
.git
.gitignore
tests
coverage
.env*

Fix 2 — Rewriting the Dockerfile

The bigger change was restructuring the Dockerfile properly around pnpm. Several deliberate decisions went into the final version:

  • Debian over Alpine. Alpine Linux uses musl libc instead of glibc, which causes compatibility issues with native Node.js modules. node:24-slim is Debian-based and sidesteps this entirely.
  • Corepack for pnpm activation. Rather than installing pnpm via npm — which is conceptually backwards — we enable it through Node's built-in corepack, the official way to manage package manager versions in Node 16+.
  • Frozen lockfile installs. The --frozen-lockfile flag ensures the container always installs exactly what's in pnpm-lock.yaml. No drift, no surprises.
  • Multi-stage build. The builder stage handles installation; a distroless runtime stage produces a lean, secure final image with no build tooling included.
Dockerfile
# ---- Stage 1: Builder ----
FROM node:24-slim AS builder

RUN corepack enable

WORKDIR /usr/src/app

COPY package.json pnpm-lock.yaml ./

RUN pnpm install --prod --frozen-lockfile \
 && pnpm rebuild \
 && pnpm approve-builds

COPY . .

# ---- Stage 2: Runtime ----
FROM gcr.io/distroless/nodejs24-debian12

WORKDIR /usr/src/app
ENV NODE_ENV=production

COPY --from=builder /usr/src/app /usr/src/app

EXPOSE 8080
CMD ["bin/server.js"]

The pnpm approve-builds gotcha

⚠️ Watch out — pnpm approve-builds in CI / Docker

pnpm blocks native build scripts by default as a security measure. Packages like deasync require a compile step, and pnpm won't run those scripts without explicit approval. Running pnpm approve-builds locally is interactive — it prompts you to review and confirm. In Docker or CI, it's non-interactive — the approvals must already exist in your project's configuration before the build runs. If you rely on this command in a Dockerfile without having committed the approval config to your repo first, the build will hang or fail silently. Commit your approvals to the repo; don't assume the interactive flow will work in automation.

What We Learned

1. pnpm failures are signals, not blockers

Every time pnpm refused to work, it was telling us something true about our project. The json-bigint error wasn't a pnpm bug — it was pnpm correctly enforcing a standard that npm had been quietly violating on our behalf. Treat pnpm install failures the way you'd treat a compiler error: not as obstacles to work around, but as information to act on.

2. Your Docker build should be hermetic

A Docker image that behaves differently from your local environment isn't a reliable Docker image. The COPY . . shortcut is convenient, but the moment it drags node_modules along, you've lost reproducibility. Every container build should install from the lockfile, inside the container, with nothing carried over from the host machine.

3. Tooling stability beats tooling currency

Jest 30 is newer and faster. Jest 29 works reliably with pnpm today. In production systems, "works reliably" wins over "latest version" — consistently. We'll upgrade when the ecosystem matures around it. We're not going to trade test reliability for a resolver we can't trust yet.

4. Run pnpm audit as part of your migration

Beyond surfacing phantom dependencies, pnpm's stricter dependency graph produces a more accurate security audit. npm's flat hoisting can introduce false positives from hoisted packages that aren't actually your problem. pnpm ties vulnerabilities to actual declared usage. Run pnpm audit and pnpm outdated after any major migration — you may find surprises.

Should You Switch?

If you're working on a production Node.js project — yes, probably. The strictness that feels like friction early on is exactly the friction that's protecting you: it's finding problems before production does.

The migration cost is real but bounded. A few hours of investigation, a handful of targeted fixes, and you end up with a build pipeline that's genuinely more reliable than what you started with. That's a trade worth making.

Just don't do it the day before a deadline.

Strict tools don’t create problems — they expose the ones you already have.
